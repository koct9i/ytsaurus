# Client API performance, limits, and throttling

This article explains why a YTsaurus client may stop scaling even though the
application can create more threads or asynchronous requests. The effective
limit is rarely one number. It is the minimum capacity of several client,
proxy, master, tablet, data-node, and network stages, some of which reject work
explicitly and some of which apply backpressure without returning an error.

The page is client-facing: it helps an application owner recognize the limit,
reduce unnecessary requests, and collect evidence before asking a cluster
administrator to change server configuration. Exact defaults are deliberately
omitted because they depend on the client implementation, cluster version, and
dynamic cluster configuration.

{% note warning "Draft" %}

Configuration names and metric paths on this page describe the native client
and server implementation. A language SDK can expose a subset under different
names. Check the configuration actually loaded by your process and the version
deployed on the cluster before changing a value.

{% endnote %}

## Performance model

Think about every workload in four dimensions:

1. **Request rate:** logical API calls and the physical RPCs generated by each
   call. One `read_table` or `write_table` call can fan out to many master,
   tablet-node, and data-node RPCs.
2. **Concurrency:** requests in flight, including requests waiting in a client
   queue, proxy queue, server queue, retry delay, or throttler.
3. **Bytes and request weight:** payload bytes are not always the unit charged.
   Some services use request count, row count, data weight, or a computed
   logical request weight.
4. **Residence time:** queue wait, throttler wait, execution time, streaming
   stall, and retry backoff all consume the end-to-end latency budget.

For a stable stage, Little's law gives a useful first estimate:

```text
required concurrency ~= target requests/second * mean end-to-end seconds
```

For streaming I/O, use bytes instead:

```text
required in-flight bytes ~= target bytes/second * round-trip seconds
```

These are starting points, not targets to maximize. Tail latency, request-size
variance, replica fan-out, and retries require headroom. Once a downstream
queue grows continuously, additional concurrency increases latency and memory
use rather than throughput.

## Explicit limits versus implicit limits

### Explicit limits

An explicit limit has a configured threshold and normally has an observable
counter, gauge, wait time, or error. Common examples are:

- per-user master `read_request_rate_limit`, `write_request_rate_limit`, and
  `request_queue_size_limit`;
- RPC service or method `queue_size_limit`, `queue_byte_size_limit`,
  `concurrency_limit`, and `concurrency_byte_limit`;
- request-count, request-weight, or request-byte throttlers;
- client reader/writer buffer sizes, parallel-reader counts, retry counts, and
  timeouts;
- response row/data limits on commands such as `list`, `select_rows`, or job
  and operation listing APIs.

Depending on the stage, reaching an explicit limit can make the request wait,
return an overload/rate-limit error, truncate a response when the API defines
that behavior, or fail with a size/row-limit error. Do not assume that every
limit produces HTTP 429 or an equivalent RPC error.

### Implicit limits

An implicit limit appears when a finite resource becomes the bottleneck even
though no quota named after the API was configured. Typical examples include:

- the calling application's thread pool, event loop, connection pool, CPU, or
  memory;
- serialization, compression, decompression, and row materialization CPU;
- a reader window or writer buffer that is too small to cover network latency;
- slow consumption of a streaming response, which fills buffers and propagates
  backpressure to the server;
- proxy CPU, bus connections, socket buffers, NIC bandwidth, or packet loss;
- master automaton time, tablet-node lookup/write capacity, data-node disk
  queues, and chunk-reader memory;
- hot Cypress paths, hot tablet keys, too many tiny chunks, or excessive request
  fan-out.

Implicit limits usually look like a plateau in throughput, increasing latency,
or increasing memory. They may not increment a single `throttled` counter.

## Where the client can be limited

### 1. Application and SDK

The first queue often belongs to the application. Synchronous calls occupy a
thread until completion. Asynchronous calls avoid one thread per request but
still need bounded admission; an unbounded collection of futures is an
unbounded queue.

SDKs also buffer and batch. Native driver configuration includes
`read_buffer_row_count`, `read_buffer_size`, and `write_buffer_size`. A batch API
may have `max_batch_row_count`, `max_batch_data_size`, and `max_batch_delay`.
Table and chunk clients add their own `max_buffer_size`, `window_size`, group
size, and parallel-reader limits.

These settings have different units and scopes. A 16 MiB buffer can be per
reader, per writer, per stream, or shared by a multi-reader. Estimate the total:

```text
process memory ~= active streams * buffers per stream + queued request payloads
```

Measure process CPU, resident memory, garbage collection, executor queue depth,
active futures, and time spent waiting for the next row. If the process is
saturated, increasing a cluster-side limit cannot help.

### 2. Client batching and fan-out

Batch independent small Cypress requests instead of issuing one RPC per path.
For dynamic tables, batch keys into `lookup_rows` and rows into
`insert_rows`/`delete_rows` while respecting request-size limits. For static
tables, use a streaming reader or writer rather than repeatedly reading or
appending tiny ranges.

Batching trades request overhead for:

- larger tail latency while a batch fills;
- larger retry and timeout blast radius;
- more memory per in-flight request;
- possible concentration on one tablet or node.

Choose a byte or data-weight bound as well as a row-count bound. Row count alone
is unsafe when values vary greatly in size. Split very large key sets by tablet
or hash when practical, and keep a small number of batches in flight rather
than one enormous request.

### 3. Client concurrency and flow-control windows

Static table reads can have several simultaneous chunks and block requests.
Relevant native settings include `max_parallel_readers`, reader
`max_buffer_size`, block-fetch `window_size`, and `group_size`. Writers have
send/window/group sizes and open chunk sessions. Dynamic-table modification
sessions additionally batch rows before committing them.

A concurrency limit controls work items; a window controls outstanding bytes.
They are not interchangeable. Large concurrency with small windows underfills
a high-latency link, while large windows multiplied by large concurrency can
exhaust memory. Increase one dimension at a time and watch active work, queued
work, throughput, and resident memory.

### 4. Timeouts, retries, and hedging

Timeouts are limits on time, not performance accelerators. A timeout shorter
than normal queue plus execution time turns successful slow work into failed
work. A very long timeout permits a large backlog and delays recovery.

Clients may have separate RPC, acknowledgement, streaming total, streaming
stall, lookup, block, probe, session, and transaction timeouts. The outer
deadline must cover the inner attempts and backoffs. Otherwise an inner retry
can start even though the caller no longer has enough time to receive it.

Retries and hedged reads multiply offered load. If the probability of another
attempt is `p`, the approximate attempt rate is:

```text
physical attempt rate ~= logical request rate * (1 + p + p^2 + ...)
```

During overload, `p` rises with latency, so immediate retries create positive
feedback. Use bounded attempts, exponential backoff, jitter, and a total retry
deadline. Retry only errors documented as transient. Preserve mutation IDs or
the SDK's idempotency mechanism for retried mutations; do not blindly retry an
unknown-outcome write.

Hedging is useful for isolated stragglers when spare capacity exists. It is
harmful when most requests are slow because it duplicates work at the exact
time the cluster is saturated.

### 5. HTTP or RPC proxy

Proxy clients add another hop and another set of connection, queue,
concurrency, byte, timeout, and streaming limits. A proxy can be healthy in
aggregate while one user, method, or backend cluster is limited. Load balancing
also matters: sticky sessions and long streams can distribute unevenly.

Distinguish:

- time waiting to acquire a client connection;
- client-to-proxy network time;
- proxy request-queue wait;
- proxy-to-backend time;
- response streaming and application consumption time.

Reusing a client and its connections is normally cheaper than constructing a
client per request. Conversely, a single shared client can become an isolation
problem if batch and latency-sensitive traffic share the same executor,
connection pool, and retry budget.

### 6. Master and Cypress request limits

Cypress metadata requests are processed by masters, directly or through a
Cypress/RPC/HTTP proxy. Users can have separate read and write request-rate
limits plus a request-queue-size limit. Servers can also throttle request bytes
or logical request weight. A batch is therefore not necessarily charged as one
unit everywhere: it reduces transport RPS but can still carry a high logical
weight.

Avoid polling attributes or existence in tight loops. Prefer a single request
for multiple attributes, cached metadata when its consistency is sufficient,
and exponential polling intervals for operation or transaction state. Avoid
large recursive `list`/`get` calls on hot paths; use pagination or bounded
result options where the API provides them.

An administrator should inspect the user's effective attributes and per-user
request metrics before raising a quota. If inefficient polling is the cause,
raising the limit merely moves the bottleneck to the master automaton.

### 7. Dynamic-table requests

`lookup_rows`, `select_rows`, and row modifications are split by tablet and
routed to tablet cells. Effective concurrency is constrained by the number of
tablets touched, per-tablet-node RPC queues, tablet lookup/write memory, store
layout, and the hottest key range. A request touching many tablets creates
fan-out and completes at the speed of its slowest subrequest.

For lookups, monitor keys and data weight per logical request, tablets and
nodes touched, client partition/retry time, tablet-node queue wait, and result
materialization CPU. For writes, also monitor commit/session latency, rows and
data weight per batch, lock conflicts, and dynamic-store pressure.

Do not use high parallelism to compensate for a hot key. Reshard, change the
key distribution, or isolate the workload. Keep transactions short: transaction
timeouts, locks, and coordinator work form limits even when row RPC throughput
is high.

### 8. Static-table and file I/O

Static-table and file clients translate one API stream into chunk metadata and
data-node RPCs. Throughput depends on chunk layout, parallel readers, fetch
windows, writer buffers, replication/erasure fan-out, data-node disk/network
throttlers, and how quickly the application consumes or produces bytes.

Use sufficiently large sequential streams and reasonably sized chunks. Many
tiny reads pay metadata, scheduling, and RPC overhead repeatedly. Many active
readers multiply buffer memory. If throttling is enabled locally, the client can
also deliberately pace data-node traffic before it reaches the server.

For detailed block-fetch, writer, bus, RPC, and data-node tuning, see
[Tuning YT bus RPC service performance for data-node table I/O](bus-rps-service-performance-tuning-draft-14.md).

## Recognizing the limiting mechanism

| Observation | Likely explanation | What to verify next |
|---|---|---|
| Throughput rises with concurrency, then plateaus while latency rises | A downstream capacity limit or queue | Per-stage queue wait, active concurrency, CPU, disk, and network |
| Immediate rate-limit or queue-limit errors | Explicit admission limit | Error attributes, user, service/method, request weight and bytes |
| Requests become slow but succeed at a steady rate | Waiting throttler or saturated implicit resource | Throttler wait, local/remote RPC wait, server execution time |
| Client CPU is full and server queues are empty | Serialization, compression, row decoding, or application work | CPU profile, executor depth, batch size, codecs |
| Client memory grows with parallelism | Per-request/per-stream buffers or unconsumed responses | Active futures, buffered bytes, consumer rate |
| Logical RPS is stable but physical RPC RPS spikes | Retries, hedging, or request fan-out | Attempt count, retry reasons, subrequests per call |
| Only one table/key range is slow | Hot tablet, chunk, path, or account-specific control | Distribution by tablet, node, chunk, and key range |
| Small requests work; large ones time out or fail | Byte/weight limit, materialization, or insufficient deadline | Request/response bytes, row/data limits, byte queues |
| Periodic latency waves | Synchronized polling/retries or refill behavior | Time correlation across clients; add jitter |

A throttler can be **hard** (rejecting admission) or **soft** (delaying it). A
soft throttler may have a burst allowance, so a short benchmark can exceed its
steady-state rate. Run long enough to exhaust burst capacity and report both
warm-up and steady-state results.

## A safe tuning procedure

1. **Name the logical operation.** Record API method, SDK and version, transport,
   cluster, authenticated user, workload category, table/path, payload
   distribution, and whether a transaction is used.
2. **Set a goal.** State target throughput and percentile latency together.
   "Make it faster" cannot distinguish throughput from latency tuning.
3. **Measure logical and physical work.** Count application calls, attempts,
   subrequests, rows, request bytes, response bytes, and data weight.
4. **Decompose latency.** Separate client admission/batching, connection wait,
   network, proxy queue, server queue/throttler wait, execution, streaming, and
   consumer time. Use request IDs and distributed traces where available.
5. **Find the first saturated stage.** A later idle stage cannot compensate for
   an earlier full one. Check the application before changing the cluster.
6. **Reduce work.** Cache, batch, remove polling, narrow columns/ranges, improve
   key distribution, and eliminate unnecessary retries before increasing a
   limit.
7. **Change one bound.** Increase concurrency, window, batch, buffer, timeout, or
   quota separately. Use a bounded canary and retain a rollback value.
8. **Load test to steady state.** Include realistic row sizes, errors, retries,
   and consumer speed. Observe neighbors and server saturation, not only client
   throughput.
9. **Add an application-side budget.** Bound concurrency and queued bytes so a
   server slowdown cannot turn into an out-of-memory failure or retry storm.

## Recommended client-side control loop

Use explicit admission control even if the cluster already has quotas:

```text
on new logical request:
    acquire concurrency slot
    acquire queued-byte budget for estimated request size
    start request with an end-to-end deadline

on transient failure and retry budget remains:
    wait for exponential backoff with jitter
    retry only if enough end-to-end deadline remains

on completion:
    record attempts, bytes, rows, and stage timings
    release byte budget and concurrency slot
```

Separate budgets for interactive and batch traffic. The application's queue
should be short and bounded; reject, shed, or defer work before it consumes all
memory. A token bucket limits arrival rate, a semaphore limits concurrency, and
a byte semaphore limits memory. Production clients often need all three.

Adaptive concurrency can reduce the limit when latency or overload errors rise,
then cautiously increase it after recovery. Cap the adaptation range and keep
server-provided retry delays. An adaptive controller is not a substitute for a
fixed memory budget.

## Common anti-patterns

- Creating a new client or transport connection for every API call.
- Launching one future per row, key, or Cypress path without a semaphore.
- Using row count as the only batch bound for highly variable row sizes.
- Retrying immediately, indefinitely, or at several nested layers.
- Raising both concurrency and retry count during an overload incident.
- Increasing a timeout without bounding the number and bytes of queued calls.
- Increasing parallel readers without calculating aggregate buffer memory.
- Treating an HTTP status alone as the diagnosis and discarding structured YT
  error attributes and request IDs.
- Benchmarking only a burst interval or from a host unlike production.
- Mixing interactive and bulk traffic under one admission and retry budget.
- Asking to raise a user quota before measuring request fan-out and eliminating
  tight metadata polling.

## Evidence to collect for an incident

Provide the following when escalating a performance problem:

- UTC interval, cluster/proxy addresses, client host or job, SDK/version, user,
  workload category, API method, path/table, and request IDs;
- logical call rate and physical attempt rate;
- concurrency, application queue depth and queued bytes;
- request and response row-count, byte, and data-weight distributions;
- p50/p95/p99 end-to-end latency, timeout/retry/hedge counts, and structured
  error codes;
- client CPU, memory, network, executor/connection-pool state, and consumer
  throughput;
- proxy and backend RPC queue wait, execution time, concurrency, request bytes,
  and throttler wait where accessible;
- effective per-user request-rate and queue-size limits for master requests;
- tablet/chunk/node distribution for table traffic and evidence of hot spots;
- the configuration delta, load-test method, and before/after measurements.

The essential question is not simply "what is the limit?" but **which unit is
limited, at which stage, for which scope, and whether the stage waits or
rejects**. Once those four facts are known, the correct response—batching,
backpressure, workload isolation, data-layout repair, or a carefully reviewed
quota change—is usually clear.
